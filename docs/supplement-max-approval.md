# Дополнительные публикации ПАРАГРАФА

## Где управлять

Пункт меню **«Доп. публикации»** (`/supplements`), также ссылка в карточке MAX-канала.

- По умолчанию: два факта (понедельник, пятница) и одна научная новость (среда), 18:00 МСК. Это время начала подготовки, а не гарантированного появления сообщения. Поиск и очередь модели занимают время.
- Расписание изначально **выключено**. Утренние статьи и их расписание не изменяются.
- Настраиваются дни, время, тематика, исключения и инструкции для каждого формата.
- Факт: одно предложение, максимум 500 символов. Новость: 2–3 предложения, максимум 1000 символов. Дополнительно публикуются 1–2 ссылки.
- В каждом материале видны источники и выдержки, поисковые запросы, снимок инструкций, история тем, объяснение выбора моделью, технические проверки, версия и решение редактора.
- Поиск использует существующие настройки Tavily, текст — существующий DeepSeek. Подготовка расходует их API-баланс. Секреты в журнал не включаются.

## Согласование

1. Платформа готовит отдельный черновик, не помещая его в общую очередь автопубликации.
2. Существующий MAX-бот присылает привязанному редактору текст со ссылками и кнопками **«Одобрить» / «Отклонить»**.
3. Одобрение сохраняется в БД и запускает фоновую отправку сразу, без ожидания следующего слота. Если брокер временно недоступен, решение подхватит минутный планировщик после восстановления.
4. Отказ или отсутствие ответа **никогда не разрешают отправку**. Одобрить через GUI нельзя.
5. Изменение текста отзывает старую версию кнопок и требует нового согласования. Чужой пользователь, старое сообщение и повторный callback решения не принимаются.
6. Перед публикацией повторно проверяются редактор, активность и адрес канала, формат и возраст источников новости. Ссылка канала разрешается в числовой ID до показа карточки.
7. Неопределённый результат MAX (таймаут/обрыв/5xx после отправки) не повторяется автоматически. В GUI нужно сначала подтвердить отсутствие поста в канале; затем бот запросит новое одобрение. Это не гарантия exactly-once внешнего API: ручная проверка обязательна.

Свежесть дат источников (до семи дней), наличие ссылок в поиске и проверка похожих заголовков — технические фильтры, **не доказательство истинности**. Редактор проверяет утверждения и дату самого события. При отсутствии подходящей датированной новости готовится факт с явной отметкой о замене. Ошибка поиска не маскируется заменой; материал получает статус ошибки. При неудачной генерации сохраняются исходные правила и причина ошибки; полный журнал исследования доступен у успешно подготовленного материала.

Перепривязка не пересылает старые ожидающие карточки автоматически: отредактируйте/перегенерируйте материал в GUI для нового редактора. Уже начавшуюся внешнюю отправку отменить невозможно. Выключение расписания останавливает новые автоматические задания, но не отменяет уже одобренные материалы; для полной остановки нужно выключить сам канал до начала отправки.

## Развёртывание и первый запуск

1. Зафиксировать и синхронизировать изменения проекта перед серверным деплоем; не затирать существующие незакоммиченные правки.
2. Сделать резервную копию БД. Применить Alembic **048** после 047 **до** запуска обновлённых API и workers: `alembic upgrade head` из backend.
3. Развернуть frontend; перезапустить API, Celery workers (очереди `celery` и `ai`) и Beat. Новая минутная задача независима от расписания статей.
4. Проверить существующий `MAX_BOT_TOKEN` и права бота на публикацию в нужном канале. Новый бот не нужен.
5. Открыть GUI → «Доп. публикации» → канал → «Подключение обработчика событий». Указать публичный HTTPS URL **этой платформы** с путём `/api/webhooks/max` и подключить. Существующие типы событий для того же URL сохраняются. Подписки на другие URL не удаляются: при смене домена их нужно проверить отдельно.
6. Секрет берётся из `MAX_WEBHOOK_SECRET`, если задан, иначе создаётся и хранится в служебной настройке БД. Из общих настроек API он исключён. Доступ к БД и резервным копиям должен быть ограничен.
7. Нажать «Получить ссылку на бота», открыть MAX и запустить бота. Ссылка одноразовая, действует 15 минут, не пересылать. В БД хранится только хеш токена привязки.
8. Проверить отображение редактора. Подготовить первый факт вручную. Проверить источники и текст в личном сообщении. **«Одобрить» действительно публикует в выбранный канал** — используйте отдельный тестовый канал для пробного полного прохода.
9. После проверки включить и сохранить расписание.

Код развёрнут на рабочем сервере 12 сентября 2026 года, миграция `048`
применена. Backend, оба Celery worker, Beat и frontend прошли проверку здоровья;
минутная задача выполняется успешно. Существующий MAX-бот обнаружен, но webhook,
привязка редактора и расписание намеренно не включались. Реальные сообщения и
публикации в MAX при развёртывании не выполнялись.

## Проверки разработки — 12 сентября 2026

- Unit и SQLite integration: сценарии одобрения, отказа, отсутствия разрешения, старых кнопок, изменения текста/канала/редактора, повторной отправки, таймаута, истечения токена и источников, расписания, источников модели и отсутствия GUI-обхода.
- Отдельная временная PostgreSQL: конкурирующие одобрения, конкурирующие publishers (одна отправка), downgrade/upgrade миграции 048 и совместимость с ORM. MAX подменён во всех тестах.
- PostgreSQL-тесты по умолчанию пропускаются; запускать только на отдельной тестовой БД через `--supplement-postgres-url`. Каждый тест создаёт уникальную схему и удаляет её после проверки.
- GUI проверен в браузере на демонстрационных API: настройки, блокировка генерации при несохранённых изменениях, редактирование и новая версия, отсутствие горизонтального переполнения на узком экране. Реальный MAX end-to-end не проверен.
- Строгий mypy новых модулей с `--follow-imports=silent` (старые модули не проверяет), black, ruff; production-сборка frontend.
- Полный набор без `tests/test_curated_publish_service.py`: девять прежних ошибок в экспорте статистики, изображениях, медиа, overview, pipeline и VK. Все девять отдельно воспроизведены на исходном HEAD; не связаны с дополнениями. Исключённый старый тест импортирует отсутствующий `app.services.scheduling_service`.
